================================================================
1. الغرض من الوثيقة
================================================================

هذه الوثيقة هي المرجع الموحد لتخطيط الموقع الرسمي لشركة atsh-ai قبل كتابة الكود.
تجمع هوية الشركة المقترحة، والخدمات، والتقنيات الأولية، وخريطة الصفحات،
وتجربة المستخدم، ومتطلبات الجودة والأمان، ومراحل التنفيذ.

قواعد العمل:
- الفصل بين القرارات المعتمدة مبدئيًا والافتراضات التي تحتاج إلى تحقق.
- عدم الإعلان عن خدمة أو منتج أو ميزة على أنها متاحة قبل التأكد من جاهزيتها.
- عدم اختلاق عملاء أو شهادات أو نتائج أو بيانات قانونية.
- عدم نسخ نصوص طويلة من مواقع المنافسين؛ تُستخدم المراجع لفهم الأنماط ثم يُكتب محتوى أصلي.
- لا يبدأ التطوير أو النشر قبل مراجعة خريطة الصفحات والمحتوى والتصميم.
- لا تُخلط مستندات الشركة ومنتجاتها مع مستودعات BOB Security؛ يبقى لكل مشروع نطاقه المستقل.

================================================================
2. تعريف الشركة والتموضع
================================================================

الاسم التجاري المبدئي:
atsh-ai

العبارة التعريفية المقترحة:
«نبني التقنية لتصنع أثرًا.»

تعريف الشركة المقترح:
atsh-ai شركة تقنية تعمل على تصميم وتطوير الحلول البرمجية والمنتجات الرقمية،
من المواقع الإلكترونية وتطبيقات الهاتف إلى الأنظمة المخصصة والحلول السحابية
والتطبيقات المدعومة بالذكاء الاصطناعي عند ملاءمتها. تجمع الشركة بين فهم احتياجات
العملاء، والتصميم العملي، والهندسة البرمجية، بهدف تحويل الأفكار إلى حلول واضحة
وقابلة للتطوير.

تعمل الشركة عبر مسارين:
1. بناء حلول ومشروعات مخصصة للعملاء.
2. تطوير منتجات رقمية تملكها الشركة ويمكن تقديمها لعدة مستخدمين أو عملاء.

تنبيه:
هذا تعريف تجاري مبدئي وليس إثباتًا للتسجيل القانوني. تُضاف البيانات القانونية
والعنوان ووسائل الاتصال الرسمية بعد التحقق منها.

مبادئ الهوية:
- هندسة قبل الوعود.
- وضوح النطاق والتسليمات.
- مراعاة الأمان والخصوصية منذ التصميم.
- تجربة استخدام واضحة.
- قابلية الصيانة والتطوير.
- الصراحة في توضيح حالة كل خدمة أو منتج.

3. محفظة الخدمات المقترحة
================================================================

هذه قائمة أولية. إطلاق أي خدمة مشروط بالقدرة الفعلية على تنفيذها ودعمها.

3.1 تطوير المواقع والمنصات الرقمية
- مواقع الشركات والمواقع الرسمية.
- صفحات المنتجات والخدمات.
- بوابات الخدمات والمنصات الإلكترونية.
- لوحات التحكم والإدارة.
- تحسين الأداء وتجربة الاستخدام وإمكانية الوصول.

3.2 تطبيقات الهاتف
- تحليل المتطلبات وتصميم تجربة الاستخدام.
- تطبيقات Android وiOS حسب النطاق.
- التكامل مع واجهات البرمجة وقواعد البيانات.
- الاختبار والتجهيز للنشر في المتاجر.
- الصيانة والتحديث وفق اتفاق واضح.

3.3 البرمجيات والأنظمة المخصصة
- أنظمة إدارة العمليات.
- حسابات المستخدمين والأدوار والصلاحيات.
- أتمتة إجراءات العمل عندما تكون مناسبة.
- تكامل الأنظمة وواجهات API.
- لوحات متابعة وتقارير.

3.4 البنية السحابية والتشغيل
- إعداد بيئات الاستضافة.
- نشر التطبيقات والخدمات.
- إعداد قواعد البيانات.
- المراقبة والنسخ الاحتياطي وخطط الاستعادة.
- إدارة بيئات التطوير والاختبار والإنتاج.
- مراجعة التكلفة واختيار الخدمات الضرورية فقط.

3.5 حلول الذكاء الاصطناعي
- دراسة حالات الاستخدام قبل اختيار النموذج.
- دمج واجهات ونماذج مناسبة في المنتجات.
- بناء مساعدات أو أدوات معالجة معلومات عند الحاجة.
- مراعاة الخصوصية وحدود الدقة والتكلفة.
- عدم وصف أي ميزة بأنها «ذكية» أو متاحة قبل اختبارها.

3.6 الاختبار والجودة والصيانة
- اختبارات آلية ويدوية بحسب المشروع.
- فحوصات الجودة والأمان المناسبة.
- مراجعة التغييرات وإدارة العيوب.
- معالجة الأخطاء والتحديثات.
- دعم ما بعد الإطلاق وفق نطاق خدمة متفق عليه.

سياسة العرض:
يمكن بدء الموقع بصفحة خدمات عامة، ثم إنشاء صفحات مستقلة للخدمات التي أصبحت
جاهزة للبيع. لا يلزم إطلاق جميع الخدمات في اليوم الأول.

================================================================
4. التقنيات الأولية المقترحة
================================================================

لا تُعد هذه القائمة قرارًا نهائيًا. يُختار المكدس التقني لكل مشروع بعد تحديد
المتطلبات والتكلفة والمهارات المتاحة ومتطلبات التشغيل.

- إدارة الكود والتعاون: GitHub.
- واجهات الويب: TypeScript مع React، ويمكن تقييم Next.js عند الحاجة.
- الخدمات الخلفية: Node.js أو Python وفق طبيعة المشروع.
- قواعد البيانات: PostgreSQL أو MySQL بحسب الاحتياج.
- تطبيقات الهاتف: Flutter أو تطوير أصلي وفق متطلبات المنتج.
- الاستضافة: Microsoft Azure أو مزود مناسب آخر بعد مقارنة التكلفة.
- CI/CD والاختبارات: GitHub Actions وأدوات ملائمة للمشروع.
- الذكاء الاصطناعي: واجهات ونماذج تُختار بناءً على حالة الاستخدام.
- مراقبة الخدمات والنسخ الاحتياطي: تُحدد وفق بنية كل تطبيق.

قواعد الاختيار:
- تجنب التعقيد والتكاليف غير الضرورية.
- لا تُفعّل خدمة مدفوعة قبل تقدير تكلفتها.
- لا تحفظ الأسرار أو مفاتيح API في مستودع الكود.
- توثيق قرارات البنية التقنية عند اعتمادها.

6. مواصفات الصفحة الرئيسية
================================================================

الهدف:
تعريف الزائر بالشركة بسرعة، وشرح قيمتها، ثم توجيهه إلى الخدمة أو المنتج أو
وسيلة التواصل المناسبة.

الترتيب المقترح:
1. شريط التنقل: الشعار، الخدمات، المنتجات، الأعمال، عن الشركة، التواصل.
2. الواجهة الرئيسية:
   - اسم atsh-ai.
   - العبارة التعريفية.
   - وصف موجز للقيمة.
   - زر «استكشف خدماتنا».
   - زر «ابدأ مشروعك».
3. قسم «ماذا نقدم؟»: بطاقات الخدمات الرئيسية.
4. قسم «منتجاتنا»: المنتجات الحقيقية القابلة للتعريف أو التجربة فقط.
5. قسم «كيف نعمل؟»: فهم الاحتياج، تحديد النطاق، التصميم، التطوير، الاختبار،
   التسليم، والدعم المتفق عليه.
6. قسم الأعمال: مشروعات موثقة أو نماذج تجريبية مع توضيح حالتها.
7. قسم دعوة للتواصل.
8. تذييل الموقع: روابط الصفحات ووسائل الاتصال والسياسات.

إذا لم تتوفر منتجات أو أعمال منشورة وقت الإطلاق، فلا تُعرض عناصر وهمية؛ يُحذف
القسم مؤقتًا أو يُستبدل بمحتوى صادق مناسب.

مسودة نص الواجهة:
العنوان:
«نبني التقنية لتصنع أثرًا.»

النص:
«نحوّل الأفكار إلى حلول رقمية عملية، من المواقع الإلكترونية وتطبيقات الهاتف
إلى البرمجيات المخصصة والمنتجات الرقمية. نجمع بين التصميم المدروس والهندسة
البرمجية والتقنيات المناسبة لبناء حلول تساعد الأفراد والشركات على العمل بكفاءة
أكبر، مع التركيز على سهولة الاستخدام والجودة والأمان وقابلية التطوير.»

الأزرار:
- «خدماتنا»
- «منتجاتنا»
- «ابدأ مشروعك»

مسودة قسم المنهجية:
«نبدأ بفهم المشكلة، ونحدد الحل، ثم نبنيه ونختبره ونطوره وفق احتياجات الاستخدام
الفعلية. نعمل على مشروعات العملاء ونطوّر منتجات رقمية خاصة بنا، برؤية تقوم على
بناء حلول مفيدة وقابلة للاستمرار والتوسع.»

هذه النصوص مسودات للمراجعة وليست موافقة نهائية للنشر.

7. مواصفات صفحة الخدمات
================================================================

يجب أن تجيب صفحة كل خدمة عن:
1. ما المشكلة التي تحلها؟
2. لمن تناسب؟
3. ما الذي سننفذه؟
4. ما المخرجات التي سيتسلمها العميل؟
5. ما الخطوات المتوقعة؟
6. ما حدود الخدمة وما الذي لا تتضمنه؟
7. كيف يطلب العميل الخدمة؟

لا تُعلن أسعارًا أو مدد تسليم ثابتة قبل تحديد النطاق وطريقة التسعير.

8. مواصفات صفحة المنتجات
================================================================

لكل منتج:
- الاسم والشعار.
- المشكلة التي يعالجها.
- الجمهور المستهدف.
- المزايا المتاحة فعلًا.
- صور حقيقية من الواجهة عند توفرها.
- طريقة الاستخدام والتسجيل.
- السعر أو الاشتراك إذا تم اعتماده.
- حالة المنتج: قيد التطوير، تجريبي، أو متاح.
- رابط الدعم والسياسات ذات الصلة.

لا يُستخدم زر «اشترك الآن» ما لم تكن آلية الاشتراك تعمل فعليًا. ويجب أن تكون
حالة المنتج واضحة للمستخدم.

- المخرجات والنتائج الموثقة.

- دور الشركة في التنفيذ.

يجب تمييز المشروعات المكتملة عن النماذج الأولية والمشروعات الداخلية. لا تُنشر
أسماء العملاء أو بياناتهم دون إذن، ولا تُختلق نتائج أو شهادات.

11. صفحة التواصل وطلب مشروع
================================================================

متطلبات التشغيل:
- توصيل الطلب إلى قناة استقبال حقيقية.
- التحقق من المدخلات وحماية النموذج من الرسائل المزعجة.
- إظهار رسالة نجاح أو فشل واضحة.
- عدم جمع بيانات أكثر من اللازم.
- عدم الادعاء بأن الطلب وصل إذا فشل الإرسال.

12. رحلة المستخدم
================================================================

المسار الأول:
الرئيسية ← الخدمة المناسبة ← تفاصيل الخدمة ← طلب مشروع ← تأكيد الاستلام.

المسار الثاني:
الرئيسية ← المنتجات ← صفحة المنتج ← تجربة أو تسجيل أو اشتراك إذا كان متاحًا.

المسار الثالث:
الرئيسية ← الأعمال والمشروعات ← دراسة حالة ← التواصل.

يجب أن تكون الدعوات لاتخاذ إجراء واضحة ومتسقة، وأن تعمل الروابط فعليًا على
الهاتف والكمبيوتر.

================================================================
13. الهوية المرئية وتجربة الاستخدام
================================================================

الاتجاه المقترح:
- هوية تقنية احترافية وليست مزدحمة.
- تباين واضح بين الخلفية والنص.
- استخدام الألوان والشعار بعد اعتماد الهوية النهائية.
- خطوط عربية وإنجليزية واضحة ومتناسقة.
- تصميم متجاوب للهاتف والكمبيوتر.
- حركة بصرية محدودة لا تؤثر في الأداء أو سهولة القراءة.
- صور أصلية أو مرخصة، وعدم استخدام صور توحي بمنتجات أو فرق أو عملاء غير حقيقيين.
- دعم RTL للعربية وLTR للإنجليزية.
- توفير حالات واضحة للأزرار والنماذج والأخطاء.

14. المتطلبات التقنية والجودة
================================================================

الأمان:

- حماية النماذج والمدخلات.
- إدارة آمنة للأسرار والصلاحيات.
- تحديث التبعيات وفحصها.
- عدم رفع كلمات المرور أو مفاتيح API إلى GitHub.

الأداء:
- ضغط الصور وتحسين أحجامها.
- تقليل JavaScript والملفات غير الضرورية.
- تجنب تحميل خدمات خارجية بلا مبرر.

إمكانية الوصول:
- تباين مقروء.
- تنقل بلوحة المفاتيح.
- تسميات واضحة للحقول والأزرار.
- نصوص بديلة مناسبة للصور.
- بنية عناوين صحيحة.

محركات البحث:
- عنوان ووصف مناسب لكل صفحة.
- روابط واضحة ومنظمة.
- خريطة موقع وملف robots عند ملاءمتهما.
- معاينات مشاركة اجتماعية.
- تجنب المحتوى المكرر.

الصيانة والتشغيل:
- تنظيم واضح للملفات والمكونات.
- بيئات تطوير واختبار وإنتاج عند الحاجة.
- اختبارات مناسبة.
- فحوصات CI/CD قبل النشر.
- نسخ احتياطي ومراقبة بحسب بنية النظام.
- توثيق خطوات البناء والنشر والتراجع.

الخصوصية:
- سياسة واضحة تتوافق مع البيانات والوظائف المستخدمة فعلًا.
- مراجعة متطلبات الخصوصية والقوانين ذات الصلة قبل الإطلاق.
- عدم وضع أدوات تتبع أو ملفات ارتباط غير ضرورية دون مراجعة أثرها ومتطلباتها.

16. مراحل التنفيذ
================================================================

المرحلة 1 — التخطيط:
- مراجعة هذه الوثيقة.
- اعتماد خريطة الصفحات.
- تحديد ما سيظهر في الإصدار الأول وما يؤجل.

المرحلة 2 — تثبيت المحتوى:

- إعداد النسخة الإنجليزية.
- تحديد الصور والرسومات والأزرار والروابط.

20. لوحة التحكم الإدارية — جزء من الإصدار الأول
================================================================

قرار تخطيطي:
تُصمم بنية الموقع منذ البداية بحيث تدعم لوحة تحكم إدارية آمنة، ولا تُضاف كحل
مرتجل بعد اكتمال الواجهة العامة. لوحة التحكم جزء من نطاق التصميم المعماري
والتخطيط الأولي، لكن وظائفها تُنفذ على مراحل بحسب الأولوية.

الهدف:
تمكين المسؤول المخوّل من إدارة محتوى الموقع الأساسي ومتابعة طلبات التواصل
والمشروعات والمنتجات دون تعديل الكود يدويًا في كل مرة.

20.1 نطاق النسخة الأولى (MVP)
- تسجيل دخول إداري آمن.
- صفحة ملخص تعرض مؤشرات تشغيلية أساسية، مثل عدد طلبات التواصل الجديدة
  وعدد المنتجات المنشورة وحالة محتوى الموقع.
- إدارة محتوى الصفحات الرئيسية: العناوين والفقرات والأزرار والروابط.
- إدارة الخدمات: إضافة وتعديل وإخفاء ونشر الخدمة.
- إدارة المنتجات: الاسم والوصف والحالة والصورة والرابط، مع حالات واضحة
  مثل «قيد التطوير» و«تجريبي» و«متاح».
- إدارة عناصر الأعمال والمشروعات مع تمييز المشروع المنشور من المسودة.
- إدارة طلبات التواصل: عرض الطلب، حالته، تاريخ وروده، وتصنيفه.
- إدارة بيانات الاتصال العامة وروابط الشبكات الاجتماعية بعد التحقق منها.
- إدارة بيانات SEO الأساسية لكل صفحة: العنوان والوصف والرابط.
- تسجيل أحداث الإدارة المهمة (Audit Log) مثل النشر والتعديل وتغيير الصلاحيات.
- حالة نشر واضحة: مسودة، منشور، أو مؤرشف.

20.2 ما يؤجل إلى مراحل لاحقة
- نظام اشتراكات ودفع إلكتروني ما لم يكن هناك منتج جاهز وخطة تجارية معتمدة.
- إدارة تطبيق الهاتف من لوحة التحكم، إلا بعد تحديد متطلبات التطبيق وتكاملاته.
- حسابات عملاء متعددة ولوحات خاصة بالعملاء.
- تحليلات متقدمة وتقارير مخصصة.
- نظام صلاحيات تفصيلي متعدد الفرق إذا لم تكن الحاجة قائمة عند الإطلاق.
- إدارة مقالات متقدمة إذا لم تُطلق صفحة المعرفة.

20.3 الأدوار والصلاحيات
- Owner/Admin: إدارة إعدادات الموقع والمستخدمين والمحتوى والنشر.
- Editor: تحرير المحتوى وإعداد المسودات دون صلاحية إدارة المستخدمين أو الأسرار.
- Support (عند الحاجة): الاطلاع على طلبات التواصل وتحديث حالتها ضمن حدود محددة.

يبدأ النظام بأقل عدد ضروري من الحسابات والصلاحيات. لا تُشارك الحسابات بين
الأشخاص، وتُمنح الصلاحيات وفق مبدأ أقل امتياز. لا تُنشأ حسابات عامة للتسجيل
الإداري المفتوح.

20.4 متطلبات الأمان للوحة التحكم
- حماية المسارات الإدارية على الخادم، وليس بإخفاء عناصر الواجهة فقط.
- استخدام مزود مصادقة موثوق أو آلية مصادقة مختبرة.
- تفعيل المصادقة متعددة العوامل للحسابات الإدارية إذا دعمها الحل المختار.
- تخزين كلمات المرور بطريقة آمنة إذا كانت المصادقة محلية، وعدم تخزينها كنص صريح.
- إدارة الجلسات والكوكيز بأمان، وحماية العمليات من CSRF عند انطباق ذلك.
- التحقق من الصلاحيات في كل عملية قراءة أو كتابة حساسة.
- تحديد معدل محاولات الدخول وحماية النماذج من إساءة الاستخدام.
- عدم تخزين مفاتيح API أو أسرار الاستضافة داخل الواجهة الأمامية أو مستودع الكود.
- تسجيل عمليات الإدارة المهمة دون تسجيل كلمات المرور أو الرموز السرية أو بيانات
  شخصية لا حاجة لها.
- توفير إجراء لاستعادة الوصول وتعطيل حساب مخترق.
- مراجعة النسخ الاحتياطي والاستعادة للبيانات الإدارية وطلبات العملاء.

20.5 تجربة الاستخدام

- بحث وتصفية وفرز لقوائم الخدمات والمنتجات وطلبات التواصل عند الحاجة.

21.1 خريطة الصفحات المقترحة

خدمة العملاء والدعم الفني:

لوحة الإدارة:
- الموظفون والحسابات والأدوار.
- الحضور والانصراف والتقارير.
- المهام والمتابعة.
- تذاكر العملاء والمحادثات.
- محتوى الموقع والخدمات والمنتجات.

21.2 الأدوار والصلاحيات

- HR: بيانات الموظفين والدوام والإجازات المصرح بها.
- Manager: متابعة فريقه ومهامه والملخصات الضرورية فقط.
- Employee: ملفه وسجل دوامه ومهامه وطلباته.
- Customer Support: تذاكر العملاء ومعلوماتهم اللازمة للحل.
- Technical Support: التذاكر الفنية والملفات المصرح بها.
- Content Editor: محتوى الموقع دون الوصول لبيانات الموارد البشرية.

يُطبق التفويض على الخادم في كل عملية، لا بمجرد إخفاء الأزرار. لا توجد
حسابات إدارية مفتوحة للتسجيل العام، ولا تُشارك الحسابات بين الموظفين.

21.3 الحضور والانصراف
- تسجيل حضور وانصراف واضح، وختم وقت خادمي لا يعتمد على ساعة المتصفح وحدها.
- سجل شخصي للموظف وسجل إداري للمخولين فقط.
- منع التكرار والحالات غير المنطقية، مع مسار استثناء موثق.
- حالات دوام قابلة للضبط حسب سياسة الشركة.
- طلب تصحيح مع سبب وموافقة مخولة وسجل تدقيق لا يمحى بصمت.
- تقارير بالفترة والفريق والموظف وفق الصلاحيات.
- اعتماد قواعد الدوام والتأخير والاستراحة والعطلات قبل أي حساب آلي.
- لا يُعتمد عنوان IP وحده دليلًا قاطعًا للحضور، ولا تُفرض جزاءات آلية دون
  سياسة معتمدة ومراجعة بشرية.

21.4 متابعة الموظفين والمهام
- مهام لها مسؤول وأولوية وموعد وحالة وتحديثات وعوائق.
- حالات مقترحة: جديدة، قيد التنفيذ، بانتظار مراجعة، مكتملة، متوقفة.
- لوحة المدير تركز على الإنجاز وجودة التسليم والمواعيد والعوائق.
- تقارير الأداء تفسر في سياق طبيعة الوظيفة وتتيح تصحيح البيانات الخاطئة.
- لا تشمل المتابعة مراقبة خفية أو تسجيل ضغطات المفاتيح أو لقطات شاشة دورية
  أو تشغيل الكاميرا/الميكروفون أو تتبع الجهاز سرًا.
- لا يُحكم على الإنتاجية بعدد النقرات أو مدة الاتصال وحدهما.

21.5 خدمة العملاء والدعم الفني
- لكل تذكرة رقم فريد وعنوان ووصف ونوع وأولوية وحالة ومسؤول وتواريخ.
- حالات مقترحة: جديدة، مفتوحة، قيد المعالجة، بانتظار العميل، مصعّدة، محلولة،
  مغلقة.
- فصل الرد الداخلي عن الرد الذي يراه العميل بصريًا ووظيفيًا.
- توزيع التذاكر والتصعيد بين خدمة العملاء والدعم الفني حسب الحاجة.
- مرفقات محدودة الحجم والنوع مع حماية الوصول وعدم تنفيذ الملفات المرفوعة.
- قياس زمن الاستجابة والحل بعد اعتماد ساعات العمل والسياسة، دون وعود وهمية.
- لا يطلب الدعم كلمات مرور أو رموز تحقق سرية من العملاء.
- إشعارات البريد أو داخل النظام لا تُعلن نجاحها إلا بعد تأكيد مزود الإرسال.

21.6 المحادثة الحية
- نافذة محادثة عامة تعرض بوضوح حالة توفر موظف الدعم.
- عند عدم التوفر، تتحول الرسالة إلى تذكرة أو طلب متابعة بدل إيهام المستخدم
  بأن هناك موظفًا متصلًا.

- حماية من الرسائل المزعجة وتحديد معدل الإرسال والتحقق من المدخلات.
- لا يُعلن دعم 24/7 إلا عند وجود تغطية تشغيلية فعلية.
- اختيار مزود المحادثة لاحقًا بعد مراجعة التكلفة والخصوصية والتكامل؛ لا يُفترض
  وجود اشتراك أو تكامل لم يُفعّل.

21.7 الإشعارات والتواصل الداخلي
- تنبيهات المهام وتغيير حالاتها.
- تنبيهات طلبات الإجازة وتصحيح الدوام عند اعتمادها.
- إشعارات التذاكر والردود والتصعيد.
- إعلانات داخلية عامة أو موجهة لفريق.
- عدم وضع بيانات حساسة في عناوين البريد أو رسائل غير آمنة.

21.8 أمن البيانات والخصوصية
- مصادقة موثوقة، ومصادقة متعددة العوامل للحسابات الإدارية متى أمكن.
- جلسات آمنة، وتحديد محاولات الدخول، وإبطال جلسات الحساب المعطل.
- حماية على مستوى كل سجل ومرفق وتذكرة، واختبارات لمنع الوصول إلى بيانات
  مستخدم آخر بتغيير المعرّفات.
- تشفير النقل، وحفظ الأسرار في إعدادات آمنة لا في ملفات Git أو الواجهة.

- تحديد غرض جمع البيانات وفترة الاحتفاظ وإجراءات الوصول والتصحيح والحذف.

  مراقبة حساسة تلقائيًا. يلزم غرض محدد وشفافية وتناسب واحتفاظ محدود ومراجعة.

21.9 البنية وترتيب التنفيذ

- تخزين خاص للمرفقات وروابط وصول محدودة عند الحاجة.
- بيئات تطوير واختبار وإنتاج منفصلة، وترحيلات قاعدة بيانات قابلة للمراجعة.
- ترتيب التنفيذ: الهوية والصلاحيات وسجل التدقيق؛ ثم الموقع ولوحة المحتوى؛ ثم
  التذاكر؛ ثم المحادثة؛ ثم الموظفون والمهام؛ ثم الحضور والتقارير؛ ثم الإشعارات

[ ] تعمل المهام وسجل التحديثات وفق الدور.
[ ] لا توجد أسرار في الواجهة الأمامية أو المستودع.
[ ] توجد سياسة خصوصية واحتفاظ ملائمة للبيانات المجمعة.
[ ] تنجح اختبارات التفويض والمرفقات والرسائل المزعجة والنسخ الاحتياطي.

22. بوابة الشركاء المُحيلين والوسطاء التجاريين
================================================================

الهدف:
إتاحة مسار منظم للوسطاء والشركاء الذين يجلبون فرص مشروعات حقيقية للشركة،
بحيث تُسجل الفرصة ومصدرها ومالك المتابعة وحالتها، وتُحسب العمولة فقط وفق اتفاق
مكتوب ومعتمد. لا تُعرض هذه البوابة كمنظومة دفع أو محاسبة مكتملة قبل تنفيذها.

22.1 واجهات الدخول
- صفحة عامة بعنوان «شركاء الإحالة والوسطاء» تشرح نموذج التعاون وتتيح طلب الانضمام.
- نموذج تقديم: الاسم، وسيلة التواصل، نوع العلاقة، الشركة إن وجدت، مجال العملاء،
  وصف مختصر، والموافقة على إشعار الخصوصية.
- بوابة خاصة للشريك بعد الموافقة وتفعيل حسابه؛ لا يوجد تسجيل دخول تلقائي إلى
  بيانات الفرص أو العمولات بمجرد إرسال النموذج.
- لوحة داخلية للإدارة لمراجعة الطلبات واعتماد الشركاء وتعليق الحسابات عند الحاجة.

22.2 وظائف بوابة الشريك
- ملف الشريك وحالة الاعتماد.
- تسجيل فرصة جديدة: العميل المحتمل، جهة الاتصال، نوع الخدمة، وصف الاحتياج،
  الميزانية التقريبية إذا عرفها الشريك، الإطار الزمني، والموافقة على مشاركة البيانات.
- منع التكرار والتنبيه عند وجود فرصة مسجلة مسبقًا، مع حسم الملكية إداريًا.
- حالات الفرصة: مقدمة، قيد المراجعة، مقبولة، تواصل جارٍ، عرض مقدم، فائزة،
  خاسرة، مؤجلة، أو مرفوضة.
- متابعة الحالة والتحديثات المسموح بمشاركتها مع الشريك دون كشف مراسلات داخلية.
- إظهار سجل الإحالات المنسوبة للشريك، والعمولة التقديرية أو المستحقة بعد اعتمادها،
  وحالة التسوية، وفق شروط العقد والصلاحيات.
- تحميل مستندات مرتبطة بالفرصة عبر تخزين خاص وصلاحيات محدودة، إذا دعت الحاجة.

22.3 قواعد تسجيل الفرص والعمولات
- لا تُضمن عمولة لمجرد إدخال اسم عميل؛ تُحدد شروط الاستحقاق في اتفاق مكتوب.
- يجب أن يوضح الاتفاق تعريف الفرصة المؤهلة، وملكية العميل السابق أو الموجود
  في قاعدة الشركة، ومدة حماية الإحالة، ونسبة أو قيمة العمولة، ووقت الاستحقاق،
  والضرائب/الفواتير إن انطبقت، وحالات الإلغاء والنزاع.
- لا يُعدل سجل نسبة العمولة أو قرار الاستحقاق دون صلاحية وسجل تدقيق.
- تظهر العمولات بوضوح كـ«تقديرية» قبل تحقق شروط العقد، ثم «معتمدة» بعد المراجعة،
  ثم «قيد التسوية» أو «مسددة» عند وجود إثبات مناسب.
- لا تُنفذ تحويلات أو مدفوعات تلقائية في الإصدار الأول دون مزود دفع معتمد
  وإجراءات مالية وقانونية واضحة.
- يجب التحقق من هوية الشريك وبياناته التعاقدية والضريبية عند الحاجة قبل التسوية،
  وفق متطلبات الشركة والقانون المنطبق.

22.4 الأدوار والصلاحيات
- Partner/Referrer: تسجيل فرصه ومتابعة حالتها والبيانات والعمولات المسموح له بها.
- Sales/Business Development: مراجعة الفرص وتحديث مراحلها وتسجيل نتائج التواصل.
- Finance: مراجعة مستندات التسوية واعتماد حالة العمولة ضمن التفويض.
- Admin/Owner: اعتماد الشركاء وإدارة السياسات والصلاحيات وسجل التدقيق.
- لا يستطيع الشريك الاطلاع على فرص شركاء آخرين أو بيانات داخلية غير لازمة.
- لا يستطيع موظف المبيعات اعتماد صرف مالي نهائي ما لم يُمنح ذلك صراحةً ضمن
  فصل صلاحيات واضح.

22.5 منع إساءة الاستخدام وحماية البيانات
- التحقق من البريد/وسيلة التواصل وموافقة الإدارة قبل تفعيل البوابة.
- تحديد معدل الطلبات وحماية النماذج من الرسائل المزعجة.
- عدم السماح برفع قوائم عملاء أو بيانات شخصية جماعية دون غرض وموافقة مشروعة.
- توثيق مصدر بيانات العميل وسبب مشاركتها مع الشركة.
- حماية ملفات العقود والعمولات، وسجل تدقيق للتغييرات الحساسة.
- سياسة واضحة للاحتفاظ ببيانات الشركاء والعملاء وإمكانية تصحيحها أو حذفها حيث يلزم.
- مراجعة قانونية للعقود والعمولات والضرائب وحماية البيانات قبل التشغيل؛ هذه
  المواصفات ليست بديلًا عن الاستشارة القانونية.

22.6 معايير القبول
[ ] يستطيع الوسيط طلب الانضمام، ولا تُمنح له صلاحية قبل الموافقة.
[ ] يستطيع الشريك المسجل تقديم فرصة ومتابعتها دون رؤية فرص الآخرين.
[ ] تُسجل مراحل الفرصة والتعديلات مع المستخدم والتوقيت.
[ ] تُفحص الفرص المكررة قبل إسناد الملكية.
[ ] لا تظهر العمولة باعتبارها مستحقة قبل تحقق الشروط واعتمادها.
[ ] تُفصل صلاحية اعتماد الشريك عن اعتماد التسوية المالية عند الحاجة.
[ ] لا توجد مدفوعات تلقائية أو بيانات مالية وهمية.
[ ] تُختبر الصلاحيات وحماية الملفات والخصوصية قبل الإطلاق.

22.7 ترتيب التنفيذ
أولًا: صفحة التعريف ونموذج طلب الانضمام. ثانيًا: اعتماد الشريك وحسابه. ثالثًا:
تسجيل الفرص ومراحلها وإسنادها. رابعًا: اتفاقيات العمولات وسجل الاستحقاق.
خامسًا: تقارير التسوية والتكامل المالي فقط بعد اعتماد السياسات.

23. قرارات المستخدم المعتمدة وتوضيحات النطاق

23.1 الهوية والنطاق
- الاسم المعتمد للاستخدام في المشروع: atsh-ai.
- النطاق الذي كتبه المستخدم حرفيًا: www.atsh.-ai.com.
- تنبيه تقني قبل ربط DNS أو النشر: الصيغة المكتوبة تبدو غير صالحة كاسم نطاق
  بسبب وجود نقطة قبل الجزء الذي يبدأ بشرطة. لا تُجرَ أي تغييرات DNS على أساس
  تخمين. يجب تأكيد النطاق الصحيح، وقد يكون المقصود www.atsh-ai.com، لكن هذا
  احتمال يحتاج تأكيدًا صريحًا وليس قرارًا تلقائيًا.
- لا تُغيّر هوية العلامة من atsh-ai بسبب اختلاف صيغة النطاق.

23.2 تعريف الخدمات
لا تُعرض الشركة باعتبارها مجرد منفذ مواقع أو باعتبارها قادرة على تنفيذ أي شيء
بلا حدود. تتمحور الرسالة حول قوة الذكاء الاصطناعي، وفهم قدراته وحدوده، وقدرة
الشركة على التعاون مع العميل وتحويل الاحتياج إلى حل قابل للتنفيذ.
يُعرض مسار العمل بوضوح: فهم المشكلة، تحديد ما إذا كان الذكاء الاصطناعي مناسبًا،
اختيار الأدوات والنموذج المناسبين، تصميم الحل، بناء نموذج أولي عند الحاجة،
التنفيذ والاختبار، ثم التسليم والدعم المتفق عليه.
يجب عدم الوعد بنتائج مضمونة أو قدرات غير مختبرة؛ ويُحدد نطاق كل مشروع وتكلفته
ومخرجاته بعد تقييم الاحتياج.

23.3 أدوار الموقع ولوحة الإدارة
تُحدد الأدوار وفق الحاجة الفعلية لإدارة الموقع وأقسامه أولًا:
- Owner/Admin: الإعدادات العامة، الحسابات، الصلاحيات، النشر، وسجل النشاط.
- Content Editor: تحرير صفحات الموقع والخدمات والمنتجات والأعمال والمسودات،
  دون إدارة الحسابات أو الأسرار.
- Leads/Business Manager: مراجعة تذاكر الاستفسارات والفرص الواردة من الموقع،
  والتواصل مع مقدم الطلب وتحديث الحالة.
- Support: متابعة استفسارات الدعم والتذاكر الموكلة إليه ضمن صلاحيات محدودة.
- Partner/Referrer: بعد اعتماد الإدارة، تقديم تذكرة إحالة ومتابعتها والاطلاع
  على ما تسمح به الإدارة من تحديثات تخص فرصته.
لا تُنشأ أدوار موارد بشرية أو مراقبة موظفين أو حضور وانصراف ضمن الأولوية الأولى
إلا عندما تعتمد الشركة حاجتها التشغيلية؛ تبقى هذه وظائف قابلة للتوسع في البنية.

23.4 نموذج الإحالة: تذكرة ثم مراجعة ثم إسناد رسمي
- نقطة البداية هي واجهة عامة في الموقع بعنوان مثل «إحالة فرصة تجارية» أو
  «تسجيل فرصة عن طريق شريك».
- يرسل مقدم الإحالة تذكرة تتضمن بياناته ووسيلة التواصل، ومعلومات الفرصة
  الضرورية، والخدمة المطلوبة، ووصفًا مختصرًا، وأي سياق مفيد، مع إقرار مناسب
  بشأن مشاركة بيانات العميل.
- تُسجل التذكرة برقم مرجعي وحالة «مقدمة»؛ ولا تعني التذكرة وحدها قبول الفرصة
  أو منح حق حصري أو استحقاق عمولة.
- تتواصل الإدارة مع مقدم الإحالة عبر وسيلة اتصال موثقة لاستكمال التفاصيل،
  والتحقق من عدم تكرار الفرصة، وتحديد إمكانية التنفيذ والتعارضات المحتملة.
- لا تُسند الفرصة ولا تبدأ التزامات العمولة إلا بعد موافقة رسمية موثقة من
  الإدارة. يصدر الإسناد الرسمي/التكليف موضحًا: رقم الفرصة، الأطراف، نطاق
  الدور المطلوب، الخدمات أو المخرجات المتوقعة، حدود الصلاحية، مدة الإسناد،
  طريقة التواصل والتصعيد، شروط السرية، ومقابل الإحالة أو العمولة إن تقرر.
- يُحفظ قرار الموافقة وتاريخه وصاحب الصلاحية ونسخة التكليف وسجل أي تعديل.
- الحالات المقترحة: مقدمة، تحتاج معلومات، قيد المراجعة، مرفوضة مع سبب مناسب،
  مقبولة بانتظار التكليف، أُسندت رسميًا، قيد التنفيذ، مكتملة، أو مغلقة.
- تُتاح لمقدم الإحالة حالة الطلب والتحديثات التي تسمح بها الإدارة فقط؛ ولا يرى
  الملاحظات الداخلية أو عروض الأسعار السرية أو بيانات عميل لا يحتاجها.
- تُحدد العمولة وشروط استحقاقها في التكليف/الاتفاق المكتوب. لا تُنشأ نسبة
  افتراضية ولا يُوعد مقدم الإحالة بالدفع قبل اعتماد الشروط.
- لا تنفذ المنظومة دفعًا آليًا في الإصدار الأول. أي تسوية مالية تخضع لاعتماد
  الجهة المخولة والإجراءات المحاسبية والقانونية ذات الصلة.

23.5 أولويات التنفيذ المحدثة
الأولوية الأولى:
1. الموقع العام ورسالة واضحة عن حلول الذكاء الاصطناعي والتعاون والتنفيذ.
2. نموذج التواصل وتذكرة إحالة الفرص مع رقم مرجعي.
3. لوحة إدارة لمراجعة التذاكر، والتواصل، وتحديث الحالة.
4. اعتماد الإدارة وإصدار تكليف رسمي محفوظ مع سجل تدقيق.
5. إدارة محتوى الموقع والأقسام والخدمات.
6. مصادقة وصلاحيات وحماية البيانات من البداية.

الأولوية التالية:
- حسابات الشركاء ومتابعة ذاتية أوسع.
- أنظمة خدمة العملاء والدردشة المتكاملة.
- بوابة الموظفين والمهام والحضور والانصراف بعد تثبيت الحاجة والسياسات.

يقدم الموقع مساعدًا آليًا لخدمة العملاء خلال ساعات العمل المعتمدة، مع واجهة
دردشة نصية تدعم إرسال المرفقات، وخيار واضح لتحويل الاستفسار إلى تذكرة رسمية.
يجب التمييز بين رد البوت الآلي ورد الموظف البشري، وعدم الادعاء بوجود موظف حي
إذا لم يكن هناك موظف متاح فعليًا.

24.1 واجهة الدردشة
- زر واضح في الموقع لفتح دردشة خدمة العملاء.
- استقبال وإرسال رسائل نصية، مع إظهار وقت الرسالة وحالة الإرسال.
- إرفاق ملفات وصور وفق قائمة أنواع مسموح بها وحدود حجم قابلة للضبط.
- إظهار تقدم الرفع ونجاحه أو فشله وإتاحة إعادة المحاولة.
- عرض إشعار واضح عند التحدث إلى بوت، وعند تحويل المحادثة إلى موظف.
- إمكانية بدء محادثة دون حساب عندما تسمح سياسة الخصوصية، مع وسيلة لاسترجاع
  المحادثة أو ربطها بتذكرة دون كشف بياناتها للآخرين.
- لا تعرض الواجهة «تم الإرسال» أو «تم إرفاق الملف» إلا بعد تأكيد الخادم.

24.2 ساعات العمل
- تُحدد ساعات العمل والمنطقة الزمنية من إعدادات الإدارة، ولا تُثبت ساعات أو
  أيام عمل افتراضية على أنها سياسة معتمدة.
- خلال ساعات العمل: يجيب البوت أولًا، ويتيح التصعيد لموظف إذا كان متاحًا.
- خارج ساعات العمل: يوضح البوت أن الخدمة البشرية غير متاحة حاليًا، ويواصل
  الإجابة عن الأسئلة العامة التي يستطيع التعامل معها، أو يقترح إنشاء تذكرة.
- تعرض الواجهة توقعًا واقعيًا للرد البشري إذا اعتمدت الإدارة هدف استجابة واضحًا.
- لا يُعلن دعم بشري على مدار الساعة دون تغطية تشغيلية مؤكدة.

24.3 سلوك البوت وحدوده
- يجيب عن الخدمات وطريقة العمل والأسئلة الشائعة باستخدام محتوى معتمد من الشركة.
- يجمع المعلومات الضرورية لفهم الاستفسار، مثل نوع الخدمة ووصف الاحتياج.
- يوضح عدم اليقين، ويحول الأسئلة التي تحتاج قرارًا أو عرض سعر أو مراجعة فنية
  إلى موظف أو تذكرة بدل اختلاق معلومات.
- لا يصدر عرض سعر نهائيًا أو وعدًا تعاقديًا أو موافقة على إحالة أو عمولة.
- لا يكشف محادثات أو ملفات مستخدمين آخرين أو معلومات داخلية.
- تُراجع الردود الحساسة، وتتاح وسيلة لطلب موظف بشري.
- لا تُرسل بيانات المحادثة إلى مزود ذكاء اصطناعي خارجي إلا بعد اختيار المزود
  ومراجعة إعدادات الخصوصية وشروط المعالجة وتقليل البيانات المرسلة.

24.4 تحويل المحادثة إلى تذكرة
- زر «تحويل إلى تذكرة» متاح من داخل المحادثة.
- تُنشأ تذكرة بمعرّف فريد، وملخص للمشكلة، ونوع الطلب، ووسيلة التواصل عند الحاجة،
  والمرفقات المسموح بها، ومرجع للمحادثة.
- يراجع المستخدم الملخص قبل الإرسال، ولا تُنسخ بيانات غير لازمة تلقائيًا.
- بعد الحفظ، يظهر رقم التذكرة وحالتها بوضوح.
- يحدد النظام نوع الطلب: استفسار عام، طلب خدمة/مشروع، دعم فني، إحالة شريك،
  أو موضوع آخر؛ ويُوجّه إلى الفريق المخول.
- تذكرة إحالة الشريك تبقى خاضعة لمسار المراجعة والموافقة والتكليف الرسمي في
  القسم 23؛ لا يوافق البوت على الإحالة ولا ينشئ تكليفًا رسميًا.
- يمكن للموظف متابعة التذكرة والرد عليها وتغيير حالتها وفق صلاحياته.

24.5 أمان المرفقات والخصوصية
- التحقق من نوع الملف وحجمه وامتداده ومحتواه قدر الإمكان، وتوليد أسماء تخزين
  آمنة، وعدم تنفيذ الملفات المرفوعة.
- تخزين المرفقات في مساحة خاصة، لا في مجلد عام قابل للفهرسة.
- التحقق من صلاحية المستخدم عند كل عملية رفع أو تنزيل؛ واستخدام روابط وصول
  محدودة المدة إذا لزم.
- وضع حدود للعدد والحجم ومعدل الرفع، وفحص البرمجيات الخبيثة حيثما أمكن.
- لا تُقبل ملفات تنفيذية أو أنواع خطرة افتراضيًا؛ وتحدد الأنواع المسموحة بوضوح.
- تنبيه المستخدم إلى عدم إرسال كلمات مرور أو رموز تحقق أو بيانات شديدة الحساسية.
- توضيح سبب جمع البيانات وفترة الاحتفاظ بالمحادثات والمرفقات، وتطبيق الحذف أو
  الأرشفة وفق السياسة المعتمدة.
- سجل تدقيق لعمليات الاطلاع والتغيير الإدارية دون تسجيل أسرار أو بيانات زائدة.

24.6 لوحة الإدارة
- إعداد ساعات العمل والمنطقة الزمنية ورسالة خارج الدوام.
- إدارة قاعدة الأسئلة الشائعة والمحتوى المعتمد للبوت.
- قائمة المحادثات والتذاكر مع الحالة والأولوية والمسؤول.
- تحويل المحادثة إلى موظف وتعيينها لفريق الدعم.
- عرض المرفقات للمخولين فقط.
- تقارير أساسية: عدد المحادثات والتذاكر، أكثر أنواع الطلبات شيوعًا، والتذاكر
  المفتوحة والمتأخرة بحسب سياسة الاستجابة المعتمدة.
- سجل تعديل إعدادات البوت والمحتوى والصلاحيات.
- لا تُعرض تحليلات أو مؤشرات غير موجودة فعليًا.

24.7 معايير القبول
[ ] تميّز الواجهة بوضوح بين البوت والموظف البشري.
[ ] تعمل الرسائل النصية مع حالات إرسال ورفع صحيحة.
[ ] تُقبل المرفقات المسموحة فقط وتُحجب عن المستخدمين غير المخولين.
[ ] تعمل الدردشة خارج ساعات العمل برسالة واضحة وخيار إنشاء تذكرة.
[ ] يؤدي تحويل المحادثة إلى تذكرة إلى إنشاء رقم مرجعي يمكن للمستخدم الاحتفاظ به.
[ ] يستطيع فريق الدعم رؤية التذاكر المسندة إليه والرد عليها وفق الصلاحيات.
[ ] لا يستطيع البوت اعتماد مشروع أو إحالة أو عمولة أو عقد.
[ ] تُختبر الحماية من الملفات الضارة والرفع المتكرر والوصول إلى ملفات الآخرين.
[ ] تُختبر سياسة الاحتفاظ والخصوصية وتُوثق قبل الإطلاق.

24.8 ترتيب التنفيذ
أولًا: نظام التذاكر وتوجيه الطلبات. ثانيًا: واجهة الدردشة النصية. ثالثًا: الرفع
الآمن للمرفقات. رابعًا: إعدادات ساعات العمل وقاعدة المعرفة المعتمدة. خامسًا:
ربط بوت الذكاء الاصطناعي بعد تحديد المزود والتكلفة والخصوصية. سادسًا: التصعيد
البشري والتقارير والاختبارات الأمنية.
