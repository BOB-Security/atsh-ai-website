# مواصفات لوحة التحكم الإدارية — atsh-ai
**الإصدار:** 1.0  
**الحالة:** مواصفات معتمدة للتنفيذ؛ ليست إثباتًا على أن لوحة التحكم نُشرت أو أصبحت متاحة.  
**النطاق:** لوحة إدارة خاصة مرتبطة بالموقع العام، مع تأمين دخول المالك عبر بريده الإلكتروني الشخصي.

## 1. الهدف
إنشاء بوابة إدارية منفصلة عن صفحات الموقع العامة لإدارة محتوى atsh-ai والطلبات والخدمات والمنتجات، مع قابلية التوسع لاحقًا لإدارة فريق العمل والعملاء. لا تعرض اللوحة أي بيانات حساسة للزائر العام.

## 2. الوصول والرابط
- مسار مقترح: `/admin`، وصفحة دخول مستقلة `/admin/login`.
- لا يظهر رابط الإدارة في التنقل العام، لكن إخفاء الرابط ليس وسيلة أمنية؛ الحماية الفعلية على الخادم.
- استخدام HTTPS فقط في الإنتاج، مع رؤوس حماية، ورسائل خطأ لا تكشف تفاصيل داخلية.
- صفحات الإدارة تتطلب جلسة صالحة وصلاحية مناسبة؛ وإلا يُعاد المستخدم إلى صفحة الدخول.

## 3. حساب المالك والتحقق بالبريد
- حساب المالك الوحيد يُنشأ من إعدادات بيئة الخادم، وليس من نموذج تسجيل عام.
- البريد الشخصي يُحدَّد في إعداد سري `ADMIN_EMAIL` بعد تأكيد عنوانه من المالك؛ لا يُخمن ولا يُكتب في المستودع.
- لا يُخزَّن أو يُرسل أي نصّ لكلمة مرور داخل GitHub أو ملفات الموقع.
- تفعيل الحساب يتم عبر رمز/رابط لمرة واحدة يُرسل إلى البريد الشخصي من مزوّد بريد موثوق، قصير الصلاحية، محدود المحاولات، ويُبطل بعد الاستخدام.
- إنشاء كلمة مرور قوية بعد إثبات البريد، وتخزين تجزئة مقاومة للتخمين (مثل scrypt/Argon2id) مع salt، لا كلمة المرور نفسها.
- استعادة كلمة المرور عبر رابط أحادي الاستخدام إلى البريد المسجل، مع صلاحية قصيرة ورسائل لا تكشف إن كان البريد مسجلًا.
- لا يجوز إعلان أن التفعيل بالبريد يعمل حتى إعداد مزوّد إرسال موثوق واختبار وصول الرسالة فعليًا.
- لا يُفعّل وضع الإنتاج إذا كانت مفاتيح الجلسات أو إعدادات التحقق الافتراضية/الضعيفة مستخدمة.

## 4. الجلسات والدفاعات
- Cookie للجلسة: `HttpOnly`, `Secure` في الإنتاج، `SameSite=Lax` أو أشد حسب تدفق الدخول.
- تدوير معرّف الجلسة بعد الدخول، وانتهاء تلقائي، وتسجيل خروج يُبطل الجلسة على الخادم.
- تحديد معدل محاولات الدخول والتحقق والاستعادة، وتأخير تدريجي وقفل مؤقت.
- حماية CSRF للطلبات التي تغيّر البيانات، والتحقق من المدخلات على الخادم، وعدم الاعتماد على إخفاء عناصر الواجهة.
- سجل تدقيق للعمليات الإدارية المهمة دون تسجيل كلمات المرور أو الرموز أو أسرار الجلسات.
- عدم استخدام كلمات مرور ثابتة أو حسابات افتراضية أو أسرار محفوظة في المستودع.

## 5. أقسام لوحة التحكم
1. **نظرة عامة:** مؤشرات الحالة وروابط سريعة، مع عدم اختلاق إحصاءات إذا لم تتوفر بيانات.
2. **محتوى الموقع:** إدارة نصوص الصفحات والعناوين والوصف باللغتين العربية والإنجليزية.
3. **الخدمات:** إنشاء/تعديل/إخفاء الخدمات، ترتيب العرض، وربط كل خدمة بصفحتها.
4. **المنتجات:** بيانات المنتجات وحالتها وروابط التفاصيل؛ ومنها BOB Security بوصفه منتجًا تابعًا لـ atsh-ai.
5. **طلبات التواصل:** عرض الطلبات الواردة وحالتها وملاحظات المتابعة بعد توصيل مصدر الطلبات بتخزين موثوق.
6. **الملفات والصور:** إدارة وسائط مسموح بها والتحقق من نوع الملف وحجمه.
7. **المستخدمون والصلاحيات (مرحلة لاحقة):** إضافة موظفين بأقل صلاحية لازمة، وعدم فتح التسجيل العام.
8. **سجل النشاط والإعدادات:** عرض الأحداث الإدارية والإعدادات غير السرية.

## 6. الربط بالموقع
- إضافة مدخل إدارة غير بارز إلى واجهة الموقع أو رابط مباشر موثق داخليًا.
- تبقى صفحات الزوار عامة ولا تتطلب تسجيل دخول.
- واجهة الإدارة تستخدم واجهات خلفية محمية؛ لا تعتمد على بيانات ثابتة داخل JavaScript بوصفها حماية.
- الحفاظ على التصميم العام ومحتوى الصفحات الحالية؛ التعديلات تكون محددة ولا تستبدل محتوى غير متعلق بلوحة الإدارة.
- إضافة اختبارات لمسارات الدخول المرفوض، والجلسة، والصلاحيات، والصفحات العامة، وفحص الصحة.

## 7. البيانات والتخزين
- استخدام مخزن دائم مناسب للإنتاج لحسابات الإدارة والجلسات والطلبات وسجل التدقيق؛ لا يُعتمد على ملفات مؤقتة في مجلد التطبيق باعتبارها قاعدة بيانات إنتاجية.
- تُحفظ بيانات الاتصال وقيم المفاتيح في إعدادات Azure App Service/Key Vault، لا في Git.
- تحديد سياسة احتفاظ وحذف للطلبات وسجل التدقيق، وقصر الوصول على المصرح لهم.
- نسخ احتياطي واختبار استعادة قبل تخزين بيانات عملاء حقيقية.

## 8. الإعدادات المطلوبة قبل التفعيل
- `ADMIN_EMAIL`: البريد الشخصي الذي يحدده المالك.
- `SESSION_SECRET`: سر عشوائي قوي وفريد.
- `EMAIL_PROVIDER_*` أو إعدادات مزوّد موثوق لإرسال رسائل التفعيل والاستعادة.
- اتصال مخزن البيانات الدائم.
- نطاق HTTPS صالح وسياسة تشغيل/مراقبة مناسبة.
تُضاف هذه القيم في Azure Configuration أو Key Vault. لا تُضاف إلى ملفات المستودع أو رسائل الدردشة.

## 9. خطة التنفيذ ومعايير القبول
1. حفظ هذا الملف مرجعًا رسميًا في المستودع.
2. بناء صفحات الإدارة والدخول وواجهات الخادم على مراحل صغيرة.
3. ربط التحقق بالبريد ومخزن البيانات الدائم من خلال إعدادات سرية.
4. اختبارات بناء ووحدات واختبارات أمنية أساسية.
5. نشر منفصل عن ربط الدومين والتحقق من `/health` ومن تدفق الدخول على عنوان Azure الافتراضي.
6. لا يُعتبر العمل مكتملًا حتى ينجح إرسال رسالة التفعيل واستلامها، وتعمل الجلسة وتسجيل الخروج والاستعادة، وتُختبر صلاحيات الإدارة فعليًا.

## 10. ما لا يُنفّذ
- لا ربط للدومين المخصص في هذه المرحلة.
- لا تخزين لكلمات المرور أو الرموز أو أسرار Azure في GitHub.
- لا إنشاء تلقائي لحساب إداري دون إثبات ملكية البريد.
- لا ادعاء بأن البريد أو لوحة التحكم تعمل في الإنتاج قبل اختبار حي موثق.
