# Azure App Service — atsh-ai

## الهدف

تجهيز استضافة Linux App Service للموقع الحالي، مع HTTPS إجباري، Node.js 24 LTS، فحص صحة على `/health`، وتعطيل FTP/FTPS. هذا الملف لا ينشئ موارد بمجرد وجوده في GitHub؛ يتم التنفيذ عبر سير العمل اليدوي.

## قبل الإنشاء

1. افتح Azure Portal وتأكد من الاشتراك الذي يحتوي رصيد Azure المتاح.
2. اختر Resource Group الحالية إن كان تطبيق `atsh-ai-website` موجودًا بالفعل. **لا تنشئ App Service ثانية بالاسم نفسه في Resource Group جديدة.** اسم تطبيق App Service عالمي وفريد، ولا يمكن نقل الملكية أو إعادة استخدام الاسم إذا كان محجوزًا بتطبيق آخر.
3. إن لم يكن التطبيق موجودًا، اختر اسمًا فريدًا مثل `atsh-ai-web-<suffix>` وأدخل الاسم نفسه في سير العمل.
4. اختر المنطقة المناسبة وتحقق من توافر App Service فيها. القيمة الافتراضية `uaenorth` (UAE North) قابلة للتغيير.
5. خطة `B1` مدفوعة وتُحسب تكلفتها حسب المنطقة والعملة والضرائب. افحص السعر في Azure Calculator قبل التنفيذ؛ لا تفترض أن الرصيد يغطي كل مدة التشغيل.

## تنفيذ البنية

من GitHub: **Actions → Azure App Service — provision and deploy → Run workflow**، ثم أدخل Resource Group الحالية، واسم تطبيق فريد، والمنطقة. سير العمل سيجري اختبارات البناء أولًا، ثم ينفذ Bicep وينشر الموقع ويختبر `/health`.

يتطلب ذلك صلاحيات Azure صالحة عبر GitHub OIDC secrets الموجودة بالفعل في إعدادات المستودع. لا تضع مفاتيح أو كلمات مرور داخل الملفات.

## قبل ربط الدومين

- تأكد أن رابط `*.azurewebsites.net` يفتح الموقع ويعيد `200` من `/health`.
- راجع صفحة **Custom domains** في App Service وتحقق من تعليمات DNS التي تعرضها Azure لهذا التطبيق تحديدًا.
- لا تعدّل DNS ولا تنشئ سجلات A/CNAME/ TXT بالتخمين. استخدم القيم التي تعرضها Azure، ثم أكمل إثبات ملكية الدومين وشهادة TLS.

## نموذج طلبات العملاء

لا تضبط `INQUIRY_WEBHOOK_URL` إلا بعد تحديد وجهة استقبال موثوقة ومحمية (CRM أو API) واختبارها. من دون ذلك، سيخبر النموذج المستخدم أن الإرسال غير مفعّل بدلًا من الادعاء بأنه حفظ الطلب.
